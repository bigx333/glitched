# Child threads

Written 2026-10-25 for review, with PR #2; brought up to main on 2026-10-29, after archiving went (Settled is where a thread done with goes) and protocol 3 was taken by that change; changed on 2026-11-03 so that only an agent starts a child and Settle takes the tree; changed on 2026-11-05 so that the engine settles and deletes a tree in one commit (open question 1); changed on 2026-11-06 for `glitched mcp`, the spawn tool's server, and so that a done or failed report wakes the parent's agent (spawn tool PR 3); changed on 2026-11-16 so that a run keeps the model and access it was admitted at, and starts no child wider (PR 90). This is what the branch builds, not a plan, except where a line says planned.

## Decision

**A child thread is an ordinary thread on the same engine with a `Parent`. The engine checks the line at create, posts each child's report into its parent's log through the outbox, and settles or deletes a thread's tree with it in one commit. The GUI does Stop all and the usage roll-up.**

- The tree is one field on the thread. Depth is never stored; it's walked, bounded.
- The engine refuses a child deeper than 4 below a thread of the user's, or wider than its parent's access or the access of the run that starts it, and a child past the configured limits (see Limits).
- A child's run that completes, fails, or blocks on a request reports to its parent as a `child.reported` event. The report is an outbox effect, committed with the child's event, so a crash replays it rather than losing it.
- Only an agent starts a child; the user can't (decided 2026-11-03). A create names the parent's live run in `ThreadCreate.Run`, and the engine refuses one that doesn't. A Claude Code agent asks through `glitched mcp`'s `delegate_task` (see The spawn tool), and the fake provider spawns for tests (`fake.Adapter.Spawns`).
- Settle and delete of a tree are one command, on the thread the user acts on. The engine applies it to that thread and every thread under it in the same commit, a child started a moment before included: settling stops each run and cancels what waits, and deleting ends each run and closes its agent. A settled tree has nothing running, and a deleted one leaves nothing behind. Stop all stays one `turn.interrupt` per thread, sent by the GUI.
- Each thread stores the tokens its own turns used. The GUI adds up a tree's.
- The protocol goes from 3 to 4, and the store schema from 4 to 5. Protocol 5 and schema 6 add the parent's last report (see Reading it). Protocol 6 has settle and delete take the tree, with no schema change (see Protocol 6).

## The parent

- `api.ThreadCreate.Parent` (`internal/api/api.go`) names the parent; zero is a thread of the user's. It's carried into `api.ThreadCreated.Parent` (`internal/api/events.go`), folded into `engine.Thread.Parent` by `apply` (`internal/engine/apply.go`), and shown as `api.Thread.Parent` by `engine.View`.
- The store keeps it in `threads.parent`, a nullable BLOB (`internal/store/store.go`). Upgrade 4 adds it with `tokens` and `reported`, after main's upgrade 3 settles the archived threads. Upgrade 5 adds `report` (see Reading it), upgrade 6 each run's `model` and `access` (see Checks at create), and upgrade 7 `commands.revision`, the target thread's revision after each command, which its receipt carries (`api.Receipt.Revision`); `schemaVersion` is 8. An older build refuses a newer database ("newer than this build").
- The parent never changes after create. There's no intent to move a thread.
- No client sends one: `Manager.Create` (`internal/client/commands.go`) makes a thread of the user's. An agent's run asks for a child with `Parent`, `Run` (the parent's live run) and `Text` (the child's first message).
- A create with `Text` queues it and admits the child's first turn in the create's own commit, under the command's ID, with the `turn.start` effect in the outbox. A crash leaves both or neither, and a retry of the same command returns the stored receipt, so one call makes one child.

## Checks at create

`store.Submit` (`internal/store/commit.go`) runs them for a `ThreadCreate` with a parent, on a thread that doesn't exist yet, in the create's own transaction:

- `lineOf` loads the parent, then its parent, up to `api.MaxDepth+1` threads, so a corrupt cycle can't hang it. A deleted ancestor above the parent ends the line, as the GUI's does: its children stand on their own. Since protocol 6 a delete takes the tree, so only a thread deleted before it leaves children like that.
- `engine.CheckChild` (`internal/engine/decide.go`) refuses, as `*api.RejectedError`:
  - "the parent thread is gone": no parent on this engine, or a deleted one. A parent on another engine is "gone" too: children are same-engine only.
  - "only the parent's live run can start a child thread, and not once it is stopping": `Run` is not the parent's live run, or that run is stopping or uncertain.
  - "a child thread can be at most N below a thread of yours": the line is longer than the limits' depth, which is at most `MaxDepth`.
  - "a child thread's access can't be wider than the run's that starts it": `Access` above the access the parent's live run was admitted at. A `thread.configure` changes a thread's model and access for its next turn. It gives only the fields its sender chose, the model's name, its effort, fast mode or the access, and the engine sets them on what the thread has when it decides (`api.ThreadConfigure.Onto`), so one sent again or chosen on an old view undoes nothing another client changed since. The run keeps its own in `engine.Run.Model` and `Access`, which `apply` sets from the thread at `turn.admitted` and the store keeps in `runs.model` and `runs.access`. Upgrade 6 fills them in from each thread's log, the create or configure last before each admission, so a stored row still equals its log's fold; a run with no admission in its log would read at Ask and its thread's model.
  - "a child thread's access can't be wider than its parent's": `Access` above the parent's as it is now, so a thread narrowed under its run narrows what the run starts. The parent's is no wider than its own parent's, so the check at one level holds for the line.
  - "N child threads of this thread are at work, the most at once; start another once one of them stops", and "this thread has N child threads, the most it may; start another once one is deleted": the parent is at a limit. `kidsOf` counts its children that aren't deleted, and those of them whose agent works: a live run that isn't uncertain. An uncertain child, as every live one is after an engine restart under Claude, has no agent at work and waits on the user, so it takes no place at once.
- A replayed create with the same command ID returns its stored receipt before any of this runs, as every command does.

## The spawn tool

`glitched mcp` (`internal/mcp`) is a stdio MCP server, newline-delimited JSON-RPC 2.0, as Zeron's `zeron mcp` is. Both binaries answer it: the CLI and the GUI.

- The host gives each run's agent the server in `provider.SessionSpec.MCP` (`runtime.WithMCP`, set by `daemon.Start`): the binary the engine runs in, with `mcp` and three variables that name the caller: `GLITCHED_THREAD`, `GLITCHED_ACCESS` (the access the agent was started at) and `GLITCHED_ENGINE` (the engine's socket). Only these name the calling thread, never a tool's arguments. They name no run: an agent's process can outlive a run and serve the thread's next one, so each call acts for the thread's live turn, and a call with no turn running is refused. An agent's access is fixed when it starts, so a call from an agent started at another access than the live turn's comes from an earlier turn's agent and is refused.
- The claude adapter passes it as an inline `--mcp-config`, without `--strict-mcp-config`, so it goes beside the user's own servers. The same `--mcp-config` takes the engine's own servers after it, each as its own inline value: the app's browser as `glitched-browser` (`docs/browser.md`, Agents), whose tools still ask. It adds `--allowedTools mcp__<name>__*` for each server marked `Trusted`, only glitched mcp, so a spawn never asks, and short instructions with `--append-system-prompt`. `claude.Command` drops any of the three variables claude would inherit, so an engine inside a run never speaks for that run's thread.
- The server answers `initialize`, `ping`, `tools/list` and `tools/call`, takes notifications, and answers any other method, such as the `server/discover` Claude Code sends first, with -32601.
- `delegate_task` takes `task`, and `title`, `provider`, `model`, `effort` and `client_request_id`. It reads the caller's thread and submits a `ThreadCreate` with `Parent`, `Run` and `Text` over the socket. A `provider` other than the turn's starts the child with none of the turn's model, effort or Fast, so that provider's program runs its own default unless the call names a model or effort; a provider, model or effort the engine's `providers` list doesn't offer is refused with the ones it does (Zeron's `TaskTarget::resolve` does the same reset). The access level carries over as it is, and each adapter maps it to its own controls. The child's model and access are otherwise the caller's turn's, `api.Thread.Turn`, the live run's as it was admitted, with the access no wider than the thread's is now; the thread's own are its next turn's. The child's thread and the command's ID derive from the call's id: `client_request_id`, else Claude Code's `_meta.claudecode/toolUseId`. So a retry finds the same child, and one whose command differs, a later turn's or one after the thread was narrowed, finds it by its thread and task. An engine refusal returns as an `isError` result with its reason.
- `TestContractMCPConfig` (claudelive) pins the merge, the tool name and the tool use id against the claude on PATH, which must be 2.1.317 or 2.1.318. Its transcript, `delegate.jsonl`, holds the MCP traffic too, which the fake claude replays against the real server.

## Worktree children

- `delegate_task` takes `isolation`: `shared`, the default, runs the child in the parent's folder, as before; `worktree` sends the create with `Worktree` set and no project or branch. T3 Code and Zeron offer the same two (Zeron `crates/mcp/src/tools/orchestration.rs:42`).
- The host makes the worktree as it makes a top-level thread's (`createInWorktree`, `internal/runtime/worktree.go`): a new branch from the HEAD of the parent's folder, so the parent's own worktree's HEAD for a parent in one, with the same ownership marker. The parent's uncommitted changes are not copied, and the tool says so. Before git runs it checks the create as the engine will, the child checks included (`store.CheckChild`). A child refused after git ran, because another took the last place under the limits meanwhile, has its worktree removed while it holds nothing new, and its branch through `git branch -d`, which keeps one with new commits or checked out elsewhere; one with changes stays, and the host logs where. A thread created in a worktree that has since been removed is refused.
- The child's project is its parent's: the folder the person chose, never a worktree under the engine's own folder, which keeps #211's rule that no project is in the engine's state folder. A parent that runs in one of the engine's worktrees with no project recorded, as a thread started from that folder by the CLI does, can't have a worktree child: the create is refused and says to start the parent from its project's folder. Its folder sits beside its parent's and the project's other threads', under the worktrees root.
- A child on a branch other than its parent's names it in its report to the parent's agent: `<task … branch="glitched/…">`. The tool text tells the parent to have the child commit there and to merge the branch.

## Task tools

- glitched mcp offers `list_tasks`, `task_status`, `task_cancel`, `task_send` and `task_answer` beside `delegate_task`, Zeron's set (`crates/mcp/src/tools/orchestration.rs`) with `task_send` for messaging a child and `task_answer` for answering its question. Each acts on a direct child of the caller's thread (`task_id` is the child's thread); `task_cancel` also stops every thread under it. The tool texts say a report comes on its own, so the agent acts on a child and never polls one. There's no blocking wait tool.
- **`task_status`** reads the child's view: working, waiting on the user (and for an approval or a question), stopping, or how its last turn ended, how many threads under it work, the questions it waits on with each one's `request_id`, what waits in its queue, `resumable` when the child is idle and a stop holds what waits, so the next message or Resume starts it (a stopping child's queue is held too, but the flag waits for the stop to land; after the user's Stop only the user can resume it), and its last report in the caller's log.
- **`task_cancel`** sends one `turn.interrupt` with `Tree` to the child, without `Drop`. It takes the child's tree as it is at its commit (`engine.TakesTree`), so a retry under the same key gets the same receipt and stops nothing new. A thread under it that the user took over, or whose run didn't answer a stop, is skipped. Queues are held, as a Stop holds them (#227), and nothing is cancelled. A stopped turn reports nothing, as the user's Stop. A `task_send` to the child releases what the stop held and its held wakes, as the user's message does.
- **`task_send`** sends a `message.dispatch` to the child, `AfterActive` by default, `SteerActive` with `mode: steer`. Its command id is derived from `client_request_id` or the tool use. The store hashes a command without its caller, so a retry sends it once, even from the agent's next turn.
- **`task_answer`** sends a `request.respond` to the child with the answers, one per question, as the user's card does. The engine refuses a caller's respond to any request but a question (`Decide`): a child's approval and credentials are the user's alone. The user sees the question too; whichever answer lands first is the one the child gets, and the other is refused as already answered. Its command id is derived as `task_send`'s is.
- **Authority, in the commit.** A command an agent sends a thread under its own carries `api.Command.Caller` (its thread and live run). The store checks it in the command's commit (`engine.CheckCaller`), as `CheckChild` checks a create: the caller's thread is above the target, the caller's run is its live run and still steerable, its run isn't a silent one, and only a message after or into the live run, or a stop without `Drop`, may name a caller, or an answer to a question. An agent never ends an uncertain run and never escalates a stop already under way: those are the user's.
- **The user's thread is theirs.** `message.queued` carries `by`, the thread whose agent sent it (a child's first message is its parent's), and every stop someone asks for leaves a `stop.asked` with `by`, whatever the run then does. The engine's own stops, such as one after an answer that couldn't be delivered, ask nothing. A caller is refused when the target's last message or asked stop has no `by`, the user's: once the user messages or stops a child, its parent's agent can't stop or message it (`steeredByUser` reads the target's log in the commit; a child's report that wakes it isn't counted). Events from before `by` existed count as the user's.
- **Which turn acts.** The agent's process can serve several turns of its thread, and nothing tells glitched mcp which turn a call belongs to. An acting tool reads the thread's live turn before anything else and acts for it, and the commit checks that turn is still live. A call made in one turn that reaches the engine only once the next has started at the same access acts for that next turn. `delegate_task` has the same limit.
- Protocol 10 (9 went to #221's `Replaces`): a version 9 engine would drop `Caller` and take the command as the user's.

## Limits

`engine.Limits` caps what agents start: 5 children of one thread at work at once, 20 in all not counting deleted ones, and depth 4, the defaults for a field of zero. Depth is at most `api.MaxDepth`. They live in `daemon.Config.Children`, saved in `engine.json` with no store schema change. `glitched serve -max-working -max-children -max-depth` sets them for the next start, and the Agents card on Settings, This machine sets them too. The engine embedded in the GUI applies a change at once through `Daemon.SetLimits`; an engine another process runs applies it when it next starts.
- A `thread.configure` that gives an access takes the tree (`engine.TakesTree`): one that narrows a thread narrows the threads under it in the same commit (`engine.Below`), and none widens them. Each live run keeps the access it was admitted at.

## Reports

When:

| The child's run | Report | Source in `Observe` |
|---|---|---|
| ends Completed | `ReportDone`, which wakes the parent | `Ended` |
| ends Failed, a failed start included | `ReportFailed`, with the error, which wakes the parent | `Ended` |
| opens a question | `ReportBlocked`, with the request's body and id, which wakes the parent | `Surfaced` |
| opens an approval or credentials ask | `ReportBlocked`, with the request's body | `Surfaced` |
| ends Interrupted or Abandoned, or ends any way while stopping | none: the user stopped it | |
| becomes Uncertain | none | |

A thread with no parent never reports.

How:

1. `decision.report` adds an `engine.ReportToParent` effect (`internal/engine/effect.go`, kind `child.report`): parent, child, run, kind, the child's title, and the error or the request body. The store writes it to `effects` in the same transaction as the child's `turn.ended` or `request.opened`. Its row is the child's, so it runs in the child's lane, in order with the child's other effects.
2. The runtime's `perform` hands it to `Host.report` (`internal/runtime/report.go`). That reads what came of the run: for a block, a line from the request body ("Wants to run …", "Wants to edit main.go", or "Asks: " and the first question); for a failure, the error; otherwise the last paragraph of what the run said last, its assistant deltas after its last tool call, which `store.RunReply` reads from the child's log (`internal/store/read.go`). It's one line, cut to 280 characters.
3. It commits `engine.Reported` on the **parent** with the effect's completion, in one transaction (`store.Observe` with `done`). `Observe` emits `api.ChildReported{Child, Run, Kind, Title, Outcome}` (`child.reported`) into the parent's log. `apply` sets `Thread.Reported` and `Thread.LastReport` (the child, the kind, and the event's seq, which `Store.write` sets on `engine.Event.Seq` before it applies the event), and bumps the revision.
4. In the same commit, a parent that was Snoozed goes back to Open. A Settled parent stays Settled: settling halted its tree, so a report into it comes from a run that ended before its stop landed. The report is still logged and counts as unread, but it moves no thread and starts no turn. A Settled thread comes back only by the user's hand (Back to inbox, or a message sent to it).
5. A done or failed report to a parent that isn't settled wakes the parent's agent, in the same commit (see Wakes).

## Wakes

A done or failed report gives the child's result to the parent's agent, as Zeron's delegate tasks do, and a question the child asks gives the parent's agent the question. There is no blocking wait tool.

- **The wake** is a message the engine queues on the parent with the report: `api.MessageQueued` with `Report` set to the child, held, in `AfterActive`. No client's message is held in `AfterActive` (a client's held message is a `Defer`), which is how the engine tells a wake from the user's words with no store schema change (`Message.waking` in `internal/engine/state.go`). Its text is the child's result in Zeron's task tags, `<task id="…" title="…" state="completed|failed"><task_result>…</task_result></task>`. The result is what the child's run said last, its text after its last tool call (`store.RunReply`), or all of why it failed. `Host.report` reads it and passes it in `engine.Reported.Reply`.
- **A question's wake** has an id of its own, derived from the request (`askWakeID`), so it and the run's later done or failed wake (`wakeID`, from the run) are two messages and neither swallows the other. Its text is `<task id="…" title="…" state="waiting_on_question" request="…"><task_question>` and each question with its options, then a line naming `task_answer`. `ReportToParent.Question` carries the request's id; an approval or credentials ask sets none and wakes nothing, as before. A wake that reaches the parent after the user answered finds the request gone, and `task_answer` says so.
- **When it runs.** `decision.settle` starts a wake when the parent is idle and nothing the user queued is ready. On an idle parent that is at once, in the report's own commit. On a parent at work, it is after the turn at work ends. Wakes that wait together go in one turn.
- **A stop stays a stop** (Nelson, 2026-11-05). When the parent's last run was stopped (ended interrupted or abandoned, or an interrupt reached it), a wake starts no turn. It waits for the user's next message and goes in with it: `decision.admit` claims every waiting wake for the turn it starts and puts their texts before the user's words, in the one turn. The agent reads the results and then the user's word on them, and the user's message is not held behind a turn of the agent's own. A user's message queued before the stop that runs after it takes them the same way.
- **Settled and deleted parents.** A settled parent takes no wake. Settling cancels the wakes that wait, with the rest of its queue, so none starts once the thread is back in the inbox. A deleted parent refuses the report, as before.
- **Once.** A wake's ID is derived from the child's run (`wakeID`), or from the request for a question's (`askWakeID`), so a report observed again, as a replayed effect's would be, finds its wake and changes nothing. A report that reached a settled parent queued no wake, so one observed again there would be logged again; the runtime commits a report with its effect's completion, so no path is known to replay one. A run ends once: only a live run ends, and boot's reconcile never ends one, so no other path reports a run twice.
- **Sent.** The engine marks a wake dispatched when the turn that carries it starts (`decision.sent`), as it marks the turn's own message. A wake in a turn that ends before it starts is released as cancelled, as a claimed message is.
- **In the GUI**, a wake is not the user's message. `client.Transcript` folds it into the report it carries (`ReportEntry.Wake`), and the report card shows one line under it: "↳ Goes to the agent after this turn", "↳ Goes to the agent with your next message" on a stopped parent, "↳ Sent to the agent", or "↳ Not sent to the agent".

Replay and failure:

- `child.report` is in `replaySafe`. A report left leased by a crash is released at boot and performed again. Because the parent's event and the effect's completion commit together, a crash leaves both or neither: the report lands once.
- Reading the child's log retries until the host closes, then the lease is released for the next host.
- A parent deleted since, as when a report is still in the child's lane when the tree's delete commits: `Observe` refuses the observation (`ErrRefused`), which still completes the effect. A parent that isn't on this engine at all: `ErrNotFound`, and `report` completes the effect itself; the create's check makes that unreachable today. Either way the child's lane moves on. `TestDelete` in `internal/engine` covers the refusal on a deleted thread; since the delete takes the child too (protocol 6), no runtime test drives a report into a deleted parent.
- There's no batching. Each report is its own event. The GUI shows a run of reports one after another as one card, a child's later report replacing its earlier one in that card (`addReport` in `children.go`). A card is keyed by its first report's child and run and by its order among that run's cards (`entriesOf` in `data.go`): a run that asks twice can start two cards, the parent's text between them, and each keeps its own pointer, focus and scroll state. The prototype batched for 2 s in memory; that's dropped.

Reading it:

- `client.Transcript` folds `child.reported` into a `*ReportEntry` and records `Transcript.Reported` (`internal/client/transcript.go`).
- A report is never updated. The card shows a blocked report as Needs you only while the child's run still has a pending request and the report is the run's last blocked one (a run that asks twice reports twice); once it's answered or the run stopped, the same card says Was waiting, with what it waited on. No event is added for it.
- `Manager.Unread` treats a report after the read mark as news, as a turn's end is; `MarkRead` and `MarkShown` read up to it (`internal/client/saved.go`).
- The parent's view carries its last report, `api.Thread.LastReport`: the child, the kind, and the event's cursor. It's committed with the event, so the shell stream sends it in commit order with every other view; the child's own view always comes first. The store keeps it in `threads.report`, JSON `{child, kind, seq}`, and stamps the cursor's log when it builds a view. Upgrade 5 fills it in from each thread's last `child.reported`, so a stored row still equals its log's fold.
- A child that waits on the user is told of by a desktop notification on the parent (`notifyAsked` in `notify.go`), unless the user is watching the parent or the child: "Write the tests: Needs you". A request ends no turn, so nothing else would tell of it; a done or failed child's turn end already notifies on the child, so its report adds none. The client tells of a child once for each of its pending requests the user has not heard of (`Manager.tell` in `internal/client/client.go`). Each child's `Thread.told` records, per pending request, whether it was told of; a request leaves it when it leaves the view, and it goes with the thread. Two things tell: the child's Blocked report, seen as its parent's `LastReport` on the shell stream, and a reconnect to the same log, which tells of each child that asks something untold, whatever the last report says. A child told of tells nothing more until it asks a new request; a Done or Failed report never tells. A shell snapshot of another log than the views held, the first connect or a restored database, tells of none: its requests count as heard, as their reports came before. A Blocked report seen after still tells of them, so a child that asked just before the app started is told of. A reconnect tells of them only for a parent whose last report moved while away, as that report may be the child's own with a sibling's after it (issue #14, fixed 2026-11-04).

## Cascades

Settle and Delete are engine-side (decided 2026-11-05, open question 1). The GUI sends one `inbox.set` or `thread.delete`, to the thread the user acts on. `store.Submit` (`internal/store/commit.go`) decides a command that `engine.TakesTree` names on every thread under its target too, in the same transaction: `treeOf` walks the threads that aren't deleted, as far down as `api.MaxDepth`, each before the thread above it, and each is decided with the same body through `engine.Decide`, so it means on each what it means on one thread. Each thread's effects go in its own lane. The commit's views go out together on the shell stream, so a client sees the whole tree change at once.

- **A child no GUI has seen**: an agent can start a child just before the user settles or deletes its tree. The child's create and the settle or delete commit one after the other under the store's lock, so the settle or delete finds the child in the table and takes it. A create after finds a settled or deleted parent and is refused (`CheckChild`). Nothing depends on what a GUI last saw, and nothing is left for a GUI to send after: a failed command that is retried takes the tree as it is then, and one dismissed leaves nothing behind (fixed 2026-11-05, PR 74 round 2, replacing the client's marks of round 1).
- **All or none**: the tree is one transaction, so a crash or a failed write part way leaves none of it, and a retry under the same ID takes all of it (`TestATreeCommitIsAllOrNothing`).

- **Stop**: the composer's Stop and ⌘↩ stop only the thread's own agent, as on main. The Agents panel's Stop all sends `turn.interrupt` to every live thread under it that shows (`stopAll`) and says how many. A stopped child reports nothing (see the table).
- **Settle** (open question 6, decided 2026-11-03): settling a thread settles it and every thread under it, its children's children too, in the settle's commit (`settleTree` sends the one `inbox.set`). The engine makes Settled mean done with (fixed 2026-11-04): in the settle's own commit it cancels the queued and held messages ("the thread was settled or deleted") and stops the live run, and it admits no turn on a settled thread. A message sent to one after is new work: in the message's own commit the engine moves the thread back to the inbox and runs it, whichever client sent it, in any mode (fixed 2026-11-04, round 2). So a follow-up another client queued just before the settle never starts, one sent after does, and a stop already under way is left to land. The engine also refuses a child under a settled parent. A thread whose agent works offers no Settle, as on main; one waiting on an approval, or left uncertain, does, and settling it stops its own run too. Back to inbox brings back that thread alone, not its tree.
- **Snooze** is unchanged: it's the user's word on that thread alone, and a report from a child brings a snoozed parent back to the inbox. A child whose agent works (`categoryOf` is Working) while the thread at the top of its line is Snoozed also shows in Working on its own, with "under <its parent's title>" beneath its title (`lifted` in `inbox.go`). Once it stops, or that thread is back in the inbox, it shows only nested again. A working thread under a lifted one shows in that one's rows, not lifted a second time. Nothing is lifted out of Settled: a working child under a settled thread can only be one another GUI left, or one the user sent a message to, and it shows nested there.
- **Delete**: the alert counts the threads under it, its children's children too ("and the 2 threads under it"), and the working ones. `deleteTree` sends one `thread.delete`, and the engine deletes every thread under it in the same commit. While it's on its way, the GUI shows none of the tree (`deleting` in `data.go` looks up the line), and a failed delete shows it all again. The engine ends each deleted thread's live run in the delete's commit, as `turn.ended` with `abandoned`, with an `agent.close` effect (`engine.CloseAgent`) in the outbox (fixed 2026-11-04). The host's pump closes the agent it holds; the effect then finds the run's agent through `Reconcile` and closes what it finds, so a crash or a shutdown before the pump's close leaves the close to the next host. It is replay-safe: closing an agent that is gone does nothing. So the delete doesn't depend on what this GUI last saw of a thread's run: a child another client just set to work goes too, a follow-up waiting its turn on a thread when its delete lands never starts, and one sent after finds no thread. Nothing waits on a stop, and there's no `afterStop`. The thread menu still offers no Delete on a thread whose own agent works, as on main.
- **Worktrees**: a child started with `delegate_task`'s `isolation: "worktree"` runs in a worktree of its own (see Worktree children). A delete that removes worktrees (`thread.delete` with `removeWorktree`, the alert's Delete worktree) removes each one of the tree's threads has of its own: the engine leaves a `worktree.remove` effect (`engine.RemoveWorktree`) for every deleted thread on a branch, after its `agent.close`, and that effect is the only thing that removes one, so a crash only delays it. Before the commit the host checks every worktree the tree owns and refuses the whole delete when one is locked, has had submodules (git won't move or remove those), isn't the one made for its thread, or has a thread outside the tree working in it. The delete answers at the commit. The effect waits for every agent that ran in the worktree to close. Then, while no worktree is made and no thread is created under the worktrees root, it keeps the worktree when a thread runs in it (the same folder by file identity, whatever the spelling), has git move it aside, and has git remove it there only when what git registers there was made for that thread on that branch; git refuses a locked one at either step, anything else is moved back, and only that worktree's registration goes. Only git deletes anything: a host that stops partway finishes on boot what git registers aside as that thread's, and keeps and logs anything else, a move git didn't finish or a partly removed worktree included. A worktree whose folder is gone leaves its branch alone, and a branch goes only through `git branch -d` in the project, so one with commits of its own or checked out elsewhere stays. Only a worktree whose folder is named by its thread's ID is removed, so a child in its parent's worktree leaves it to the parent, and a child that kept its worktree in its own delete keeps it when its parent's tree goes. The alert offers Delete worktree when any thread of the tree has one of its own, and names them, with... (line truncated to 2000 chars)
- **Failure**: a settle or delete that fails to reach the engine shows on the thread the user acted on, as main's failed commands do, with Retry and Dismiss. Its tree is untouched until a retry lands.
- A thread whose parent was deleted before protocol 6 stands on its own: `parentOf` finds no parent, it shows at the top level, and `treeOf` stops at a deleted thread, as `lineOf` does.

## Usage

- `provider.TurnEnded.Tokens` → `engine.Ended.Tokens` → `api.TurnEnded.Tokens`. `apply` adds it to `Thread.Tokens`, stored in `threads.tokens`, shown as `api.Thread.Tokens`.
- `app.usage` (`children.go`) adds up a thread's and every thread's under it at read time. The header shows "1.2k · 3.6k with children".
- No real provider reports tokens yet. The fake reports `Adapter.Tokens`, and `daemon.Defaults` sets it to 1800 so the dev engine shows something.

## Protocol 4

- `turn.interrupt` gains `drop` (omitted when false). An engine of this protocol cancels what waits its turn on it and stops the run; on a run already stopping it adds no second interrupt, so the run ends as its agent does rather than going uncertain. No GUI path sends it since settle and delete stop runs themselves (2026-11-04); it stays in the protocol. `drop` is new inside protocol 4 and an engine built from this branch before f62ba50 ignores it (protocol 4 is unreleased, so no bump).
- `api.Protocol` is 4. The transport already refuses a peer of another protocol in both directions, so a protocol 3 GUI shows a protocol 4 engine as Incompatible, and the reverse. A protocol 3 hub refuses the uploads.
- Why refuse rather than stay at 3: a protocol 3 client would list children as threads of the user's and drop the reports (unknown event types are skipped), which looks like lost work.

## Protocol 5

- `api.Thread.LastReport` is new. `api.Protocol` is 5: a protocol 4 GUI would drop the field and tell of reports from `Reported` and the children's requests, which is issue #14, so it is refused.

## Protocol 6

- A settle or a delete takes the thread's tree in its commit. `api.Protocol` is 6: a protocol 5 GUI sends a command per thread, which an engine of 6 has already taken, and a protocol 5 engine would leave a child of a settled or deleted thread at work behind a protocol 6 GUI's one command. So each refuses the other. No store schema change.
- `api.MessageQueued.Report` (spawn PR 3) is new within protocol 6, with no release in between. A client that drops it would show a wake as the user's message.

## Remote children (placeholder)

A child on another machine starts as a placeholder here (design: the captain's remote-children handoff, PR 2). Its create and follow are in "Remote children (created and followed)".

- `api.ThreadCreate.Remote` names a machine by its label in `machines.json` (`daemon.Machines`). The daemon has the store read the file at each remote create, in its commit (`Store.SetPlaces`), so a machine removed takes no more, and takes each machine's engine and link ids, never its token. A file that can't be read, or holds a machine without its label, server, engine or link, refuses only remote creates and is logged once. `store.Submit` runs `CheckChild` as for any child, and decide refuses a label not in the list.
- The placeholder is a child with `Remote` set (`api.ThreadCreated.Remote`, `engine.Thread.Remote`, `threads.remote`, schema 16) and no run, ever: its task is for the other machine, so nothing queues it here. `threads.origin` is the other machine's side and stays null.
- Decide takes a placeholder in its own branch for every intent. Settle, delete, rename and configure go as for a child, so settling or deleting the tree takes it in the one commit. A message or a stop is refused until it can reach the machine. A stop of the tree passes it by (`engine.Below` is nil).
- `kidsOf` counts a placeholder that is creating as at work.
- `Host.Submit` refuses a remote create whose task or title holds any value of the parent's vault, literally and whatever its length, before anything is stored. It commits under the lock a worktree create holds, so a local create of the same thread that is making its worktree commits first.
- Protocol 17: a version 16 GUI would show a placeholder as a child here with an empty transcript.

## Remote children (on the machine they run on)

A link (`api.Link`, minted with `daemon.PairLink`) lets another machine's engine start threads here (design: the captain's remote-children handoff, PR 3). Nothing on that machine dials here yet; tests call this engine through the link's token as it would.

- A link's socket may call `info`, `read`, `subscribe`, `submit` and `child.reply` (`transport.linkMethods`), and each checks in `runtime.Host` that the link started the thread it names: `Origin.Link` is the link's id. A query or subscription with no thread, a thread of anyone else's, and a child under the link's thread are refused with `api.ErrNotAllowed`.
- `submit` takes the closed link create on a new thread, and on a thread the link started a message, a stop, an inbox set or a configure that only narrows its access, checked against the thread as the configure's own commit has it (`Store.SubmitChecked`), so a narrowing by B's person a moment before is never undone. A settle or a narrowing takes the threads under it through the tree walk, as for any thread. Each command id is a hash of the link's id and its own, so no receipt crosses links.
- The link create gives `Origin{Engine, Thread, Title, Depth, Access}`, `Repository{Root, Branch}`, `Title`, `Model`, `Access` and `Text`, nothing else. The host stamps `Origin.Link` from the token, matches the repository by its root commit among the folders the person's threads run in (one checkout, worktrees of one clone counting as one), and finds the branch's commit. Only a link sends an origin.
- The create's commit reads the link in `tokens.json` as it is then (`Store.SetLinks`), narrowed to `children_from_other_machines`, so a socket that outlived a revoke by its last second creates nothing. It checks `Origin.Depth` is 1 to the depth limit, the access against the origin's and the link's, and the link's `Working` and `All` counted by `Origin.Link` (zero takes the child limits).
- It commits the thread with `Origin` (`threads.origin`, making), its first message and a `worktree.make` effect, and admits nothing. The effect makes the thread's branch at the base with `update-ref`, its reflog's first entry naming the thread, adds the worktree on it locked, the thread in the lock's reason, writes the owner file and unlocks, then `worktree.ready` gives the thread its folder and branch and the message starts. A replay finishes a worktree locked for its own thread, on its branch, whose owner file is absent or names it, or one it finished, and removes the empty folder a kill as git began leaves, taking up a branch a kill left when its reflog names the thread and it is at the base in no worktree. A branch of anyone else's under either name, a worktree locked for anything else, owned by another thread, on another branch or holding changes, stays as it is, and `worktree.failed` cancels what waited. A thread settled before its worktree was begun never gets one; one settled while git made it gets it finished, and starts nothing.
- For its life a link's thread runs no wider than the lowest of `Origin.Access`, its link's current ceiling and the current setting (`engine.Env.Ceiling`, read at each commit). A message over a lowered ceiling waits, a steer into a run admitted above it is refused, and a configure that raises the thread past it is refused from anyone. The same ceiling holds every thread under it, at every admission, steer and configure: the store finds the link's thread up the line in each commit (`originOf`), so a revoke or a lowered ceiling holds the whole tree.
- `CheckChild` adds `Origin.Depth` to a line that starts at a link's thread, so the depth limit holds across both machines, and refuses a remote child under one.
- `child.reply{Thread, Run}` is `store.RunReply` for a run of the thread.
- Protocol 18.

## Remote children (created and followed)

The parent's engine creates a placeholder's child on its machine and follows it there (design: the captain's remote-children handoff, PR 5).

- `delegate_task` takes `machine`, one of the labels in `machines.json` when the agent started (`GLITCHED_MACHINES`, labels only). It sets `ThreadCreate.Remote` and leaves the workspace, project and branch to the other machine. A machine with `isolation: "shared"` is refused: no folder is shared across machines.
- The placeholder's create commits a `remote.create` effect holding the frozen link create: its command id and thread id derive from the placeholder's, `Origin` is this engine, the parent, its title, its depth and the lower of the parent's and the run's access, and `Repository` is the parent's folder's root and branch. A parent on no branch of a repository with a commit, or with no live run, is refused.
- The effect records its first try (`remote.attempted`) before it dials, and none once the placeholder is settled or deleted without one. It sends the same command until the machine answers: a receipt binds the placeholder (`remote.bound`), a refusal loses it. A kill before the receipt leaves the effect leased; the next boot replays it, and the other machine's receipt for that command id means one thread there.
- A bound placeholder has a follower: it subscribes to the child's thread from the cursor the placeholder stores, folds what it reads with `engine.Follow` under the local rules (a done or failed end reports unless stopping, silent or uncertain; a request reports blocked unless silent), asks `child.reply` for each done run, and commits `remote.seen` with the cursor, run, slot, the requests the run waits on and the keys it reported. A worktree the other machine couldn't make reports failed. It checks every second, and before each commit, that the machine is still in `machines.json`. A child settled there before its first run takes no place at work here. A reply the machine no longer has (a restore of its database) is retried, and the next read finds the restored log. A report is delivered once per key (the run, or the request), across restarts, snapshots and a restore of the other machine's log. A snapshot's fence is committed once.
- A blocked child's report says it runs on the machine, where the user answers it: `task_answer` doesn't reach it there yet.
- Every failed call goes through `runtime.classify`. A network failure retries on `WithRemoteBackoff` (2s doubling, capped at 5m) forever. A refused handshake loses the child the second time in a row. A refusal, `ErrNotAllowed`, `ErrConflict`, `ErrNotFound`, a machine that answers as another engine or link, or one gone from `machines.json` loses it at once. Three defects in a row (an internal error from a handler, a fold that fails, a panic) lose it as a child that may still run there. Progress, a network failure or a refusal starts the defect count over; progress, a network failure, a defect or a catch-up starts the refusal count over.
- A lost placeholder (`remote.lost`) reports failed once, saying why.
- `kidsOf` counts a placeholder creating, or bound with its child's slot neither idle nor uncertain, as at work. A bound placeholder starts at `starting`, and so does a child whose worktree is being made, so it counts before the first read.
- The placeholder's `thread.created` holds its task (`Text`), so a `delegate_task` retry in a later turn finds it.
- The link's token stays in `machines.json` and the dialer: never in the store, a log, an effect or an agent's environment.
- No wire change between engines beyond protocol 18; the `remote.*` events are this engine's own, and a version 18 client decodes them as unknown and skips them. Protocol stays 18, schema 16.
- Not yet: a stop, message, settle, delete or configure toward the other machine, and answering its questions from here.
